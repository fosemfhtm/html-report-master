# 서술 구조

## 1. 이전 실패의 원인

| 원인 | 결과 |
|---|---|
| **데이터 중심 구성.** 프롬프트 원문, 함수 이름, 격자 같은 실제 기록을 그대로 올렸다. | 정확하지만 청중이 가져갈 메시지가 없었다. |
| **이끄는 질문의 부재.** 기능을 차례로 소개하면서, 각 기능이 생긴 이유를 빠뜨렸다. | 청중이 장면마다 필요성을 모른 채 넘어갔다. |
| **뒤에 놓인 결론.** 장치 설명이 대부분을 차지했다. | 청중은 지친 뒤에야 결론을 봤다. |
| **용어와 숫자 기준의 과다.** 새 용어와 기준이 다른 숫자를 한꺼번에 썼다. | 청중이 모두 기억해야 화면을 읽을 수 있었다. |
| **덧붙이기식 수정.** 피드백마다 문장과 장면을 더했다. | 분량만 늘고 메시지는 흐려졌다. |
| **흩어진 아이디어.** 참고 사례, 구현 수단, 제품 방향을 한자리에 섞었다. | 제품 하나의 그림이 서지 않았다. |
| **제품과 무관한 외부 조사.** 시장 조사 표를 본문에 넣었다. | 우리 제품을 그리는 데 쓰이지 않았다. |
| **이야기 평가 전 제작.** 사용자의 구상을 듣자마자 만들기 시작했다. | 사용자가 처음부터 구성을 다시 설명해야 했다. |
| **겹치는 글의 층.** 한 장면에 꼬리표, 제목, 부제, 자막, 라벨을 함께 두었다. 제목과 자막은 같은 말을 되풀이했다. | 읽을 글이 늘고 초점이 흐려졌다. |
| **연결 없는 문장.** 장면마다 문장이 따로 섰다. | 이야기가 이어지지 않았다. |
| **나열.** 문장마다 "무엇을 한다"만 적었다. | 줄인 뒤에도 "설명을 해 줘야지"라는 평을 받았다. |
| **번역투.** 대상 주어, 수동형, 영어 표현 직역을 썼다. | 같이 작업한 사용자도 문장을 이해하지 못했다. |

## 2. 글의 층별 역할

| 층 | 역할 |
|---|---|
| 장 번호, 꼬리표 | 위치 표시 |
| 제목(h2) | 장의 주제, 명사형 |
| lead, 자막 | 설명: 무엇을 하는지와 그 이유, 결과 |
| 그림, 표, 라벨 | 숫자와 구조 |
| 주석(note) | 출처, 실제/예시 구분 |

층마다 다른 일을 맡긴다. 맡을 일이 없는 층은 지운다.

## 3. 장별 한 문장 표

HTML 작업 전에 사용자에게 승인받는 기획 산출물이다.

예: 신호 최적화 웹앱 기획 보고서 (가상의 예)

| # | 장 | 청중이 가져갈 한 문장 | 본문 자료 | 부록 또는 삭제 |
|---|---|---|---|---|
| 1 | 이전 작업 | SUMO 기반 웹앱으로 학습·재생·비교까지 구현, 외부 연동 구조와 재생 파일 크기가 한계 | 주요 화면 4장, 구현·한계 카드, 접속 링크 | 화질 낮은 영상 |
| 2 | 기반 | 엔진과 화면이 한 프로그램이라 같은 데이터·API로 바로 연결 | 장점 카드 3개, 기존 시각화 화면 3장 | 엔진 구조 상세 |
| 3 | 방향 | 코딩하지 않는 실무자가 TOD·RL을 실행하고 현재 신호와 비교하는 도구 | 핵심 문장 상자, TOD·RL 비교표 | 시장 조사 표 |
| 4 | 데모 | 지도 한 화면에서 탐색·학습·비교·교차로 분석 진행 | 보고서 안 데모, 클릭 순서 5단계 | 데모 안 질문 |
| 5 | 질문 | 워크플로우·설정 범위·지표에 대한 의견 요청 | 질문 카드 3개(선택지·제안안), 다음 단계 | 막연한 의견 요청 |

## 4. 장 하나의 구성

```
번호 · 이름        3 · 제품 방향
제목(h2)           코딩 없는 신호 개선 도구
결론(lead)         알고리즘 선택, RL 학습, 결과 재생·비교까지 구현한 이전 시도.
근거               한 문장을 뒷받침하는 그림, 표, 카드
주석(note)         데이터 출처, 실제/예시 구분
```

- 제목과 lead만 이어 읽어도 보고서 전체 이야기가 성립해야 한다.
- 앞 장의 결론이 다음 장의 질문이 되게 잇는다. 예: 앞 장의 결론이 "후보 정책은 읽기 쉽고 가볍다"이면, 다음 장은 "성능 좋은 후보를 찾는 방법"에 답한다.
- 카드 제목에는 판단(구현 내용, 한계)을, 카드 안에는 사실을 적는다. 근거 수치는 사실 옆에 작은 글씨로 단다.

## 5. 보고서 흐름의 예

사용자가 순서를 정하면 그 순서를 따른다. 정하지 않았으면 자료를 보고 정한다. 논문 해설이면 논문의 흐름을 따른다. 아래는 제품 기획 보고서에서 잘 맞았던 흐름이다.

1. **이전 작업.** 실제 화면, 구현한 기능, 한계와 그 원인.
2. **현재 기반.** 이번에는 다르게 만들 수 있는 이유.
3. **제품 방향.** 대상 사용자와 제품을 한 문장으로 정의한다. 혼동하기 쉬운 개념은 비교표로 나눈다.
4. **사용 장면.** 클릭 가능한 데모 또는 연속 화면에 실제/예시 데이터 표시를 단다.
5. **결정 사항.** 질문 세 개 이내와 질문마다 선택지·제안안, 다음 단계.

지면은 3~4장, 곧 사람이 제품을 쓰는 장면에 가장 많이 배정한다.

## 6. 자료 처리

- **실제/예시 태그.** 실제 실행 결과에는 `실제`, 가상 결과와 제안 화면에는 `예시`를 단다. 데모 위에는 범례 한 줄을 둔다.
- **데이터 근거.** 모든 값은 데이터에서 가져온다. 예시 값에는 산출 근거를 주석으로 단다. 예: "재생 데이터의 정지 차량 수로 만든 예시".
- **레퍼런스.** 다른 제품에서는 문제를 푸는 방식과 UI·UX를 배운다. 참고 화면 한 장과 우리 시안 한 장을 나란히 두고, 결론 하나를 적는다.
- **이미지.** 주요 화면을 캡처해 넣고, 누르면 확대되게 한다. 원본 서비스로 가는 링크는 버튼으로 단다.
- **질문.** 마지막 장에 모은다. 질문마다 질문 내용, 판단 기준, 선택지와 제안안을 적는다.
- **세부 내용.** 한두 문장에 담기지 않는 수치와 절차는 발표 대본(.md)과 부록에 보존한다.

## 7. 검토 방식

- **전체 제시.** 실제로 쓸 문장을 번호를 붙여 전부 보여 준다. 장면별 대표 문장만 보여 주면 사용자가 전체 분량을 판단할 수 없다.
- **수정 제시.** 고친 문장은 "지금 / 문제 / 고친 문장" 표로 보여 주고, 그대로 둔 번호도 적는다.
- **오류 정정.** 확인하지 못한 내용과 앞선 분석의 오류는 먼저 밝히고 바로잡는다.
- **유형 단위 수정.** 사용자가 한 문장을 짚으면 같은 유형의 문장을 전체에서 찾아 함께 고친다.
